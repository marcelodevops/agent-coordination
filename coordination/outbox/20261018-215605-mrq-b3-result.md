## What was wrong, reproduced first

**Python.** `python -m build` on the generated project *did* succeed before the
fix, but the artifact was not a usable application: the wheel shipped a bare
top-level `main.py` with **no importable package**, **no tests**, and **no
installed entrypoint** — so the README's `pip install -e .` / run commands and
the Dockerfile's `CMD` had nothing to invoke. Root cause: setuptools
auto-discovery over a `src/` tree containing a loose module.

**Rails.** `config/application.rb` interpolated the project name straight into
`module $name`, so any hyphenated identity generated invalid Ruby. Reproduced
with the host interpreter:

```
$ ruby -c old_style.rb          # module my-app / class Application
old_style.rb:1: class/module name must be CONSTANT
module my-app
       ^~
old_style.rb:1: syntax error, unexpected '-'
module my-app
         ^
ruby rc=1
```

## Python reference starter (real commands, verified natively)

`bootstrapper/templates.py` → `python-microservice` (aliased as `python`), plus
the honest description
`"Python starter package (src layout, tests, Dockerfile, CI); a starting point,
not a production microservice"`.

Layout: `src/appstarter/{__init__.py,main.py}`, `tests/test_appstarter.py`,
`pyproject.toml` (PEP 621, `[project.scripts] appstarter`, explicit
`[tool.setuptools] packages` + `package-dir` so auto-discovery cannot regress),
`.env.example`, `.gitignore`, `Dockerfile`, GitHub CI. `src/main.py` is retained
as a thin compatibility shim because accepted tests depend on its presence.

**Import package is deliberately `appstarter`, independent of the distribution
name.** A hyphenated identity like `my-app` is not a legal Python module name,
so deriving the package from `$name` would recreate the Rails-class bug. README
and template both state this.

## Rails: the narrow honest experimental option (no runtime claim)

Host Ruby is **2.6.10**; `rails ~> 7.1` requires **>= 3.1**, and per the
assignment I installed nothing and changed no host setup. A runnable Rails
starter therefore cannot be verified here, so the profile is explicitly scoped
as an experimental layout rather than claimed as an app:

- Template description → `EXPERIMENTAL Rails-style layout only (not runnable,
  not \`rails new\` output)`.
- Generated README carries a `## Status: experimental layout, not a runnable
  Rails app` section plus a `### Missing preparation` list:
  `config/environment.rb`, `config/boot.rb`, `config/routes.rb`, `bin/rails`,
  `Rakefile`, `app/views/`, `db/`, Ruby >= 3.1, `bundle install`.
- `config/application.rb` now declares the stable constant `module AppStarter`
  (name is not interpolated, with a comment explaining why).

Evidence is **syntax-only**, and I am not calling it runtime verification:

```
$ ruby -c railsapp/app/controllers/application_controller.rb → Syntax OK
$ ruby -c railsapp/config/application.rb                     → Syntax OK
```

`rails server` was never executed; no boot was observed. One test does load the
file with a stubbed `Rails::Application` to prove the declared module name is a
real constant (`[A-Z]\w*`), asserting the property rather than mirroring the
literal name — it is a parse/definition check, not proof that Rails works.

## Limits

- Native Python checks are guarded by `skipif` when uv/`build` are absent and
  print a reason. **A skip is not a pass**; on this host all ran (shown above).
- Docker image build was **not** executed. `test_docker_and_ci_commands_are_coherent`
  only proves the Dockerfile/CI text matches commands proven to work outside
  Docker; it cannot and does not claim `docker build` succeeded.
- No framework, no business logic, no dependencies added beyond
  stdlib + pytest/build at dev time — this is a starter, described as one.
- `appstarter` is a fixed package name for every project by design. Making it
  name-derived would require `render()` logic in `templates.py`'s substitution
  layer, which is A2-owned; I did not reach into it.
- Rails remains an experimental layout. It becomes a supported profile only when
  a host with Ruby >= 3.1 can actually run `rails new`/`rails server` and the
  generated app boots — deliberately out of scope here.
- No commits, pushes, publishes, remote/network actions, installs of Rails, or
  host changes.
